We keep that shape and that export contract; everything else is rebuilt to look/feel like a real institutional admin portal.

## 7. Risks (assumptions the brief makes that the code does not fully guarantee) and safe fallbacks

- **No `sl-act-btn--publish` / `sl-act-btn--archive` CSS class.** The brief's class list implies them but `dashboard.css` only defines `sl-act-btn`, `sl-act-btn--edit`, `sl-act-btn--toggle`, `sl-act-btn--del`. Fallback: use base `sl-act-btn` with inline stroke colors for publish/archive/download (the current file already does exactly this), and `sl-act-btn--edit` for the edit pencil.
- **`getConsultationStats(id)` returns only `{ responseCount }` — no per-question aggregation helper exists.** The brief asks to "click to see aggregated answers via getConsultationWithQuestions/getConsultationStats," but neither returns response rows. Fallback: use `getConsultationWithQuestions(id)` for the question list and `getConsultationStats(id)` for the count, plus an inline `supabase.from('consultation_responses').select('question_id,answer').eq('consultation_id',id)` query (the `consultation_responses` row shape is knowable from `submitResponse`: `consultation_id, question_id, answer, is_anonymous`) to tally per question. If that inline query is rejected at build/runtime, degrade gracefully to count + question list only. Decision rationale: keeps this a true single-file change and matches the codebase's direct-Supabase pattern (`governance.js` itself imports `supabase`).
- **No `updateQuestion` / `reorderQuestion` / `deleteQuestion` lib functions.** The question builder can only *add* questions (`addQuestion`). Fallback: reorder is applied to a local copy of the questions array for display; persistence of a new order is limited to inserting new questions with the intended `sort_order`. Document this limitation in a UI hint; deleting/reordering existing questions is out of scope without a lib addition. (Adding lib functions is out of scope for this single-file rewrite.)
- **`consultation_questions` column names are not declared in the lib.** `addQuestion` does `insert({ ...question, consultation_id })`, so whatever fields the component sends must match the DB columns or the insert throws. The builder will send `{ question, type, options, sort_order }` as the conventional names; if the real schema differs (e.g. `text` instead of `question`, `choices` instead of `options`), the create will fail at runtime (not at build). Fallback: keep the payload minimal and named conventionally; surface the Supabase error via the error toast so the column mismatch is visible and fixable. This does not block the build.
- **`target_deadline` / `assigned_to` / `internal_notes` columns on `concern_submissions`.** `updateConcernStatus` accepts and writes these, so the columns exist; `getAllConcerns` selects `*`, so the fields are present on returned rows. Low risk. Fallback: guard with `||` defaults when rendering.
- **"Publish Now" semantics for drafts.** `publishDocument` sets `status:'published'` + `approved_by` + `published_at`, so a one-click draft→published publish is supported by the lib directly (it does not require a `submitted` intermediate). Implement Publish Now as a direct `publishDocument(id, user?.username)` call; the brief's "quick approve + publish in one click" is satisfied by skipping the submitted/approved intermediates.
